"테트리스 게임 하나 만들어 줘."

바야흐로 '대 딸깍의 시대'야. 프롬프트 한 줄, 엔터 한 번이면 AI가 알아서 코드를 줄줄 짜내는 세상이지. 자연스럽게 우리가 직접 키보드를 두드리며 코드를 만질 일은 줄어들었고, 그만큼 `git add`, `git commit` 같은 명령어를 칠 일도 눈에 띄게 줄었어.

그렇다면 이제 Git은 몰라도 되는 걸까? 결론부터 말하자면 **절대 아니야. 오히려 AI가 코딩을 주도할수록 소프트웨어 공학의 꽃인 '버전 관리'는 훨씬 더 중요해져.**

AI는 아직 완벽하지 않거든. 멀쩡히 잘 돌아가던 코드를 한순간에 망가뜨리기도 하고, 엉뚱한 로직을 짜놓고 다 했다고 태연하게 거짓말을 하기도 해. 이런 AI의 잦은 실수와 폭주를 수습할 수 있는 유일한 생명줄이 바로 Git이야.

오늘은 터미널에 직접 Git 명령어를 치지 않더라도, AI 에이전트를 효과적으로 통제하고 프로젝트를 탄탄하게 이끌어갈 수 있는 **4가지 핵심 전략**을 소개해 줄게.

---

## 1. 사고를 방지하는 안전망: GitHub Flow 도입하기

AI에게 통째로 코딩을 맡길 때 가장 위험한 행동은 메인(`main`) 코드베이스에 직접 수정 사항을 들이붓는 거야. 이때 필요한 게 바로 **GitHub Flow**지.

{{< figure src="ghflow_illustration.png" alt="GitHub Flow 프로세스를 보여주는 일러스트 이미지" caption="GitHub Flow 워크플로우 (Gemini로 생성된 AI 이미지입니다.)" align="center" >}}

GitHub Flow는 복잡한 브랜치 전략을 단순화해서 'Pull Request(PR)' 중심으로 작업하는 방식이야. 코드를 바로 본진에 밀어 넣는 대신, 새 브랜치에서 안전하게 작업하고 PR을 올려 검토를 받은 뒤 병합(Merge)하는 구조야.

인간이 매번 이 리뷰 루프에 개입하면 개발 속도에 병목이 생길까 걱정돼? 걱정 마. 요즘은 **이 PR 리뷰 절차마저도 별도의 AI 에이전트(리뷰 봇)에게 맡겨서** 안전하면서도 매끄러운 자동화 개발 파이프라인을 구축하는 추세니까.

### AI에게 GitHub Flow를 강제하는 프롬프트

AI 코딩 어시스턴트의 시스템 프롬프트나 에이전트 지침 파일(`AGENTS.md` 등)에 아래 스니펫을 추가해 봐.

```text
앞으로 모든 코드 작업은 GitHub Flow를 엄격하게 따릅니다.
1. 절대 `main` 브랜치에 직접 코드를 작성하거나 푸시하지 마세요.
2. 새로운 기능이나 버그 수정 시 반드시 `feature/기능명` 또는 `fix/버그명` 형태로 새 브랜치를 생성하고 작업하세요.
3. 작업이 완료되면 `main` 브랜치를 향한 Pull Request(PR) 생성을 준비하고 저에게 리뷰를 요청하세요.
```

## 2. AI의 '딴짓'을 막는 나침반: GitHub Issue와 백로그 관리

"테트리스 만들어 줘"라고 뭉뚱그려 명령하면 AI는 십중팔구 중간에 길을 잃어버려. 안 만들었는데 만들었다고 우기거나, 요구하지도 않은 이상한 기능을 덧붙이곤 하지.

이런 참사를 막으려면 AI 시대에도 기존의 SDLC(소프트웨어 개발 수명 주기)를 따라야 해. 즉, 다짜고짜 코딩을 시키는 게 아니라 "테트리스 게임을 구현하기 위한 요구사항을 먼저 정리해 줘"라고 문서화부터 시작하는 거지.

이때 도출된 요구사항이나 기능 명세서를 바탕으로 GitHub Issue를 생성해 백로그(Backlog)로 활용해 봐. 프로젝트의 마일스톤이 한눈에 들어오고, 현재 AI가 어디까지 작업했는지 명확하게 추적할 수 있어. 운영 단계의 버그 리포트뿐만 아니라, 개발 단계의 내비게이션으로 Issue를 쓰는 거야.

### Issue 체계화를 위한 GitHub Sane Label 적용 프롬프트

Issue는 '어떤 카테고리인가(분류)'와 '무엇을 해야 하는가(내용)'가 핵심이야. 무작정 라벨을 만들지 말고, `platform:`, `priority:`, `type:` 같은 접두사(Prefix)를 붙이는 Sane Label 방식을 적용하면 관리가 훨씬 편해져.

```text
현재 프로젝트의 GitHub 저장소에서 사용할 Sane Label 목록을 세팅해 줘.
'type:', 'priority:', 'platform:' 접두사(prefix)를 반드시 포함해서 체계적으로 분류하고, 각 라벨에 어울리는 색상 코드(HEX)와 짧은 설명을 마크다운 표로 정리해 줘.
```

### 명세서 기반 백로그(Issue) 자동 생성 프롬프트

설계가 어느 정도 끝났다면, 그 문서를 바탕으로 일감을 쪼개달라고 요청해 봐.

```text
[요구사항 명세서 텍스트 입력]
위 명세서를 바탕으로 개발 단계에서 사용할 GitHub Issue 백로그 리스트를 작성해 줘.
AI 에이전트가 하나씩 맡아서 처리할 수 있는 적절한 작업 단위로 쪼개고, 앞서 정의한 Sane Label(type, priority 등)을 각 태스크마다 알맞게 지정해 줘.
```

## 3. 히스토리를 읽기 쉽게: Conventional Commits (커밋 컨벤션)

프로젝트에 여러 사람이 투입돼서 제각각의 말투로 커밋 로그를 남기면 나중에 히스토리를 추적하기가 끔찍해지잖아? 이걸 해결하기 위해 나온 규칙이 바로 **Conventional Commits(관례적 커밋)**야.

AI는 지치지 않고 엄청난 속도로 코드를 짜고 수많은 커밋을 생성해 내. 문제는 이 커밋 메시지들이 중구난방이면 우리가 최종 결과물을 해석할 길이 없어진다는 점이지.

설령 우리가 코드를 한 줄 한 줄 읽어낼 능력이 부족하더라도, AI가 남겨놓은 커밋 로그만큼은 명확하게 읽고 "아, 여기서 UI를 수정했고 저기서 에러를 잡았구나"라고 파악할 수 있어야 해. 일관성 있는 템플릿(규칙)을 적용하면 이게 가능해져.

| 타입(Type) | 설명 (AI에게 기대하는 작업 분류) | 커밋 메시지 예시                             |
| :--------- | :------------------------------- | :------------------------------------------- |
| `feat`     | 새로운 기능 추가                 | `feat: 테트리스 블록 회전 로직 추가`         |
| `fix`      | 버그 또는 오류 수정              | `fix: 블록이 바닥을 뚫고 내려가는 버그 수정` |
| `docs`     | 문서 수정 (README 등)            | `docs: 요구사항 명세서 업데이트`             |
| `refactor` | 코드 리팩토링 (기능 변화 없음)   | `refactor: 충돌 감지 함수 구조 개선`         |
| `chore`    | 설정 파일, 패키지 매니저 등 수정 | `chore: 패키지 의존성 업데이트`              |

### AI에게 커밋 단위와 컨벤션을 강제하는 프롬프트

AI는 가만히 두면 여러 작업을 한 번에 뭉뚱그려 커밋하는 경향이 있어. `AGENTS.md`나 작업 지시서에 아래 규칙을 추가해 주면 나중에 프로젝트 타임라인을 돌아볼 때 겪을 스트레스의 90%를 덜어낼 수 있어.

```text
모든 Git 커밋은 아래 규칙을 반드시 준수하세요.
1. 한 번에 모든 변경 사항을 통째로 커밋하지 말고, 논리적인 최소 작업 단위(Atomic Commit)로 쪼개서 커밋하세요.
2. 커밋 메시지는 반드시 Conventional Commits 규칙(feat:, fix:, docs:, refactor:, chore: 등)을 따르세요.
3. 특정 GitHub Issue를 해결하는 작업이라면 커밋 메시지나 PR 본문에 `Closes #이슈번호`를 명시하세요.
```

## 4. 지시와 보고의 표준화: Issue Template & PR Template

자, 이제 Issue로 일감을 만들고 PR로 결과물을 받는 흐름은 알겠지? 그런데 여기서 한 단계 더 나아가서 AI의 작업 품질을 극적으로 끌어올리는 치트키가 있어. 바로 `.github` 폴더 안에 **Issue Template**과 **PR Template**을 세팅해 두는 거야.

사람끼리 일할 때도 업무 요청서 양식과 결과 보고서 양식이 정해져 있으면 소통 비용이 확 줄어들잖아? AI 에이전트에게는 이 템플릿이 **가장 완벽한 구조화 프롬프트(Structured Prompt)** 역할을 해.

### Issue Template: AI에게 건네는 '표준 작업 지시서'

`.github/ISSUE_TEMPLATE/` 경로에 마크다운이나 YAML 파일로 이슈 양식을 만들어 두면, AI가 이슈를 생성하거나 읽을 때 **빠뜨리기 쉬운 맥락과 완료 조건(Acceptance Criteria)**을 명확하게 짚어줄 수 있어.

- **배경 및 목적 (Context)**: 왜 이 기능이 필요한가?
- **상세 요구사항 (Requirements)**: 구체적으로 무엇을 구현해야 하는가?
- **완료 조건 (Acceptance Criteria)**: 어떤 테스트를 통과해야 작업이 끝난 것으로 인정할 것인가?

특히 **완료 조건(체크리스트)**이 핵심이야. 이게 없으면 AI는 코드가 돌아가는 척만 하고 작업을 끝내버리거든.

```markdown
<!-- .github/ISSUE_TEMPLATE/feature_request.md 예시 -->

## 📌 작업 개요 (Overview)

- 구현할 기능에 대한 한 줄 요약을 작성합니다.

## 🎯 상세 요구사항 (Requirements)

- [ ] 키보드 위쪽 방향키(↑)를 누르면 테트리스 블록이 시계 방향으로 90도 회전해야 함
- [ ] 벽이나 다른 블록과 겹치는 위치에서는 회전이 제한되어야 함

## ✅ 완료 조건 (Acceptance Criteria)

- [ ] 모든 종류의 블록(I, O, T, L, J, S, Z)에서 회전 동작 확인
- [ ] 경계면 회전 시 배열 인덱스 에러가 발생하지 않을 것
```

### PR Template: AI가 제출하는 '셀프 검증 보고서'

반대로 `.github/pull_request_template.md` 파일은 AI가 코드를 다 짜고 PR을 올릴 때 **스스로 자신의 작업을 돌아보고 요약하게 만드는 검문소**야.

AI에게 PR 템플릿을 채우도록 강제하면, 코드를 짤 때 미처 생각하지 못했던 사이드 이펙트나 누락된 테스트를 PR 작성 단계에서 스스로 발견하고 고치는 효과를 볼 수 있어. 인간 디렉터 입장에서도 코드 수백 줄을 다 읽는 대신, AI가 정리한 PR 요약본만 보고 빠르게 승인(Merge) 여부를 판단할 수 있지.

```markdown
<!-- .github/pull_request_template.md 예시 -->

## 🔗 관련 이슈 (Related Issue)

- Closes #이슈번호

## 🛠 변경 사항 요약 (Summary)

- 이번 PR에서 어떤 파일과 로직을 왜 수정했는지 핵심만 요약합니다.

## 🧪 검증 및 테스트 내역 (Test Plan)

- [ ] 기존 기능이 깨지지 않는지 확인했는가?
- [ ] 이슈에 명시된 완료 조건(Acceptance Criteria)을 모두 달성했는가?
- [ ] 불필요한 디버깅 코드나 임시 파일이 포함되지 않았는가?
```

### AI에게 Issue & PR 템플릿 세팅을 시키는 프롬프트

이 템플릿 파일들조차 우리가 직접 짤 필요는 없어. 프로젝트 시작할 때 아래 프롬프트 한 번이면 AI가 알아서 `.github` 디렉토리 구조를 깔끔하게 잡아줄 거야.

```text
현재 프로젝트에 AI 에이전트 기반 개발 워크플로우를 위한 GitHub 템플릿을 세팅해 줘.
1. `.github/ISSUE_TEMPLATE/feature_request.md`와 `bug_report.md`: 작업 배경, 상세 요구사항, 그리고 명확한 완료 조건(Acceptance Criteria) 체크리스트가 포함되도록 작성해 줘.
2. `.github/pull_request_template.md`: 연결된 이슈 번호(Closes #), 변경 사항 요약, 그리고 AI가 스스로 테스트 여부를 점검할 수 있는 체크리스트를 포함해 줘.
앞으로 모든 이슈 생성과 PR 작성 시 이 템플릿 양식을 엄격하게 지켜서 작성해.
```

> **실전 꿀팁: AI가 직접 GitHub에 이슈와 PR을 올리게 하려면?**
> 터미널에 **GitHub CLI(`gh`)**를 설치해 두거나 코딩 에이전트에 **GitHub MCP**를 연동해 봐. 웹 브라우저를 켜서 복붙할 필요 없이, AI가 직접 터미널에서 이슈를 조회(`gh issue view`)하고 템플릿에 맞춰 PR 생성(`gh pr create`)까지 알아서 척척 끝내줄 거야.

## 마치며

결국 오늘 이야기한 4가지는 따로 노는 게 아니라 **하나의 완벽한 사이클**로 맞물려 돌아가.

1. **GitHub Issue & Template**으로 할 일과 완료 기준을 명확히 정의하고,
2. **GitHub Flow**에 따라 독립된 브랜치를 파서 안전하게 작업한 뒤,
3. **Conventional Commits**로 깔끔한 발자국을 남기며,
4. **PR Template**을 통해 스스로 검증된 결과 보고서를 제출받아 병합하는 것.

'딸깍' 한 번으로 코드가 완성되는 시대가 왔지만, 그 코드를 관리하고 프로젝트가 올바른 방향으로 굴러가게 만드는 버전 관리의 본질은 변하지 않았어.

직접 터미널에 `git commit`을 타이핑하지 않더라도, 오늘 소개한 규칙들을 너의 AI 에이전트에게 적용해 봐. AI라는 뛰어난 주니어 개발자를 완벽하게 리드하는 든든한 시니어 디렉터가 될 수 있을 거야.
