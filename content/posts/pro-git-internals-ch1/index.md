현업에서 매일 `git add`, `git commit`, `git push`를 입력하면서도 정작 Git이 내부적으로 데이터를 어떤 구조로 저장하고 왜 이런 명령어 인터페이스를 갖게 되었는지 명확히 설명할 수 있는 개발자는 많지 않다. *Pro Git*은 Git의 내부 원리까지 가장 정확하게 다룬 교과서지만, 바쁜 실무 속에서 두꺼운 원서를 처음부터 끝까지 정독하기는 쉽지 않다.

이 시리즈에서는 *Pro Git*을 레퍼런스로 삼아, 실무 개발자가 반드시 알아두어야 할 Git의 내부 구조와 동작 원리를 세세하게 파헤친다. 첫 번째 글에서는 **Pro Git 1장**(Getting Started)의 세 섹션(1.1~1.3)을 바탕으로, Git이 왜 지금과 같은 형태로 태어났고 데이터를 어떻게 바라보는지 근본적인 철학부터 짚어본다.

---

## 1. 버전 관리 시스템(VCS)의 진화: 왜 분산형이었어야 했나?

버전 관리 시스템(VCS, Version Control System)은 시간의 흐름에 따라 파일의 변경 이력을 기록해 두고, 나중에 특정 시점의 버전을 다시 꺼내 볼 수 있게 해주는 시스템이다. 파일이 망가졌을 때 복구하거나, 특정 버그를 누가 언제 유입시켰는지 추적하는 데 필수적이다. Pro Git은 VCS의 발전 과정을 세 단계로 구분한다.

### ① 로컬 버전 관리 (Local VCS)

가장 원시적인 버전 관리는 타임스탬프를 붙인 디렉토리에 프로젝트 전체를 복사해 두는 방식이다. 단순하지만 작업 디렉토리를 착각해 파일을 덮어쓰는 실수가 잦다. 이를 해결하기 위해 로컬 디스크에 간단한 데이터베이스를 두고 파일 변경 이력을 관리하는 로컬 VCS가 등장했다.

대표적인 도구가 지금도 유닉스 계열 OS에 흔히 남아 있는 **RCS**다. RCS는 디스크에 특수한 포맷으로 **패치 셋**(Patch sets, 파일 간의 차이점)을 저장하고, 시점이 지정되면 처음부터 모든 패치를 순서대로 합산해 해당 시점의 파일을 재구성한다. 하지만 여전히 모든 데이터가 개발자 한 명의 로컬 머신에만 존재한다는 한계가 있었다.

### ② 중앙 집중식 버전 관리 (CVCS)

여러 개발자가 협업해야 하는 문제가 대두되면서 **CVS, Subversion(SVN), Perforce** 같은 중앙 집중식 VCS(CVCS, Centralized VCS)가 표준으로 자리 잡았다. 모든 버전 관리 파일이 담긴 단일 중앙 서버가 존재하고, 여러 클라이언트가 그 서버에서 파일을 체크아웃(Checkout)해 작업하는 구조다.

- **장점**: 누가 무엇을 작업하고 있는지 파악하기 쉽고, 관리자가 세밀한 접근 권한을 통제할 수 있으며, 클라이언트마다 로컬 DB를 관리하는 것보다 운영이 편하다.
- **치명적 단점**: 중앙 서버가 **단일 장애점**(SPOF, Single Point of Failure)이 된다. 서버가 1시간 다운되면 그 시간 동안 누구도 협업하거나 변경 사항을 커밋할 수 없다. 만약 중앙 DB의 디스크가 손상되고 백업이 없다면, 각 개발자 PC에 남아 있는 단편적인 스냅샷을 제외하고 프로젝트의 전체 히스토리가 완전히 소실된다.

### ③ 분산 버전 관리 (DVCS)

이 단일 장애점 문제를 정면으로 해결한 것이 **Git, Mercurial, Darcs** 같은 분산 버전 관리 시스템(DVCS, Distributed VCS)이다.

DVCS에서 클라이언트는 단순히 최신 파일 스냅샷만 받아오는 것이 아니라, **전체 히스토리를 포함한 저장소 자체를 로컬에 완전히 미러링**(Mirroring)한다. 덕분에 서버가 죽더라도 어떤 클라이언트의 저장소든 다시 서버로 복사해 완벽히 복구할 수 있다. 즉, **모든 클론(Clone)이 곧 전체 데이터의 풀 백업**이다. 나아가 여러 개의 원격 저장소(Remote)를 동시에 연결해 다양한 협업 워크플로우를 구축할 수 있는 유연함까지 얻게 되었다.

## 2. Git의 탄생: 리누스 토르발스가 세운 5가지 설계 목표

Git의 탄생 배경은 오픈소스 역사에서 가장 유명한 일화 중 하나다. 거대한 오픈소스 프로젝트인 리눅스 커널은 초창기(1991~2002년)에 변경 사항을 단순 패치 파일과 압축 아카이브로 주고받으며 유지보수했다. 그러다 2002년부터 **BitKeeper**라는 상용 분산 버전 관리 도구를 무료 라이선스로 도입해 사용하기 시작했다.

하지만 2005년, 리눅스 커널 커뮤니티와 BitKeeper 개발사 사이의 관계가 틀어지면서 무료 사용 권한이 철회되었다. 이 사건을 계기로 리누스 토르발스(Linus Torvalds)를 비롯한 리눅스 개발 커뮤니티는 BitKeeper에서 얻은 교훈을 바탕으로 직접 새로운 도구를 만들기 시작했고, 이때 다음 5가지 명확한 설계 목표를 세웠다.

1. **속도 (Speed)**
2. **단순한 설계 (Simple design)**
3. **비선형 개발에 대한 강력한 지원**: 수천 개의 병렬 브랜치를 동시에 다룰 수 있어야 한다.
4. **완전한 분산 구조 (Fully distributed)**
5. **대규모 프로젝트의 효율적 처리**: 리눅스 커널처럼 방대한 프로젝트를 속도와 데이터 크기 양면에서 감당할 수 있어야 한다.

2005년 탄생 이후 Git은 이 초기 철학을 단 하나도 훼손하지 않은 채 오늘날의 표준으로 자리 잡았다.

## 3. Git이 데이터를 바라보는 방식: Delta가 아닌 Snapshot

Pro Git 1.3에서 가장 강조하는 대목이다. 다른 VCS(Subversion, CVS, Perforce 등)를 써본 개발자일수록 Git의 CLI가 비슷해 보여서 같은 방식으로 동작할 것이라 착각하기 쉽다. 하지만 **Git이 내부적으로 데이터를 저장하고 사고하는 방식은 기존 VCS와 완전히 다르다.**

{{< figure src="delta-vs-snapshot.svg" alt="기존 VCS(Delta 기반)와 Git(Snapshot 기반)의 데이터 저장 방식 비교 다이어그램" caption="기존 VCS(Delta 기반)와 Git(Snapshot 스트림)의 데이터 저장 구조 비교 (Pro Git 1.3 도식 재구성)" width="820" height="560" >}}

### 기존 VCS: Delta 기반 (파일별 변경 이력 저장)

대부분의 기존 VCS는 데이터를 **파일 집합과 각 파일에 시간순으로 가해진 변경 사항의 목록**으로 저장한다. 즉, 기준 버전(Base version)에 `Delta 1`, `Delta 2`, `Delta 3`를 더해 나가는 **Delta 기반**(Delta-based) 버전 관리 방식이다.

### Git: Snapshot 스트림 (미니 파일시스템)

반면 Git은 데이터를 변경 사항의 목록으로 보지 않고, **작은 파일시스템의 연속적인 스냅샷**(Stream of snapshots)으로 취급한다.

- 사용자가 커밋을 할 때마다 Git은 그 순간 프로젝트의 모든 파일이 어떤 모습인지 사진(Snapshot)을 찍어 그 스냅샷에 대한 참조를 저장한다.
- 효율성을 위해, **이전 커밋과 비교해 변경되지 않은 파일은 다시 저장하지 않고 이미 저장해 둔 동일한 파일로의 링크(포인터)만 기록**한다.

이 차이는 단순히 저장 포맷의 차이가 아니다. 덕분에 Git은 단순한 버전 관리 도구를 넘어 **강력한 도구들이 올라간 하나의 미니 파일시스템**(Mini filesystem)처럼 동작하며, 이후에 살펴볼 초고속 로컬 브랜칭과 머지의 토대가 된다.

## 4. Git의 내부 동작을 지탱하는 3가지 철학

스냅샷 모델과 분산 구조 위에서 Git은 세 가지 강력한 동작 특성을 갖는다.

### ① 거의 모든 작업이 로컬에서 수행된다

Git의 대부분 명령어는 로컬 디스크의 파일과 리소스만 있으면 실행된다. 네트워크 너머의 다른 컴퓨터와 통신할 필요가 없다.

프로젝트 히스토리를 조회하거나 한 달 전 파일과 현재 파일의 차이(`diff`)를 계산할 때, Git은 원격 서버에 요청을 보내거나 과거 버전을 내려받을 필요 없이 **로컬 데이터베이스에서 직접 찾아 즉시 계산**한다. 덕분에 속도가 압도적으로 빠르며, 비행기 안이나 VPN이 끊긴 오프라인 환경에서도 아무런 제약 없이 로컬에 커밋을 쌓으며 작업할 수 있다. (Perforce나 Subversion처럼 서버 연결이 끊기면 커밋조차 불가능한 구조와는 근본적으로 다르다.)

### ② Git은 무결성(Integrity)을 보장한다

Git에서는 모든 데이터가 저장되기 전에 체크섬(Checksum)을 계산하며, 이후에는 파일 이름이 아니라 그 체크섬으로 데이터를 참조한다. 즉, Git이 모르게 파일 내용이나 디렉토리 구조를 단 1비트라도 변경하거나 전송 중 손상시키는 것은 불가능하다.

이 무결성 검증 메커니즘이 바로 **SHA-1 해시**다. 파일 내용이나 디렉토리 구조를 기반으로 계산된 40자리의 16진수 문자열(`0–9`, `a–f`)이다.

```text
24b9da6552252987aa493b52f8696cd6d3b00373
```

핵심은 **Git이 데이터베이스에 모든 것을 '파일 이름'이 아니라 '내용의 해시값'으로 저장한다**는 사실이다. 이 Content-Addressable(내용 기반 주소 지정) 구조는 Git 내부 객체 모델을 이해하는 열쇠가 된다.

### ③ Git은 기본적으로 데이터를 추가(Add)만 한다

Git에서 어떤 작업을 수행하든, 거의 대부분의 동작은 Git 데이터베이스에 **새로운 데이터를 추가**할 뿐 기존 데이터를 지우지 않는다. 커밋하지 않은 변경 사항을 날려버릴 수는 있어도, 한 번 스냅샷으로 커밋하고 나면 데이터를 영구히 잃어버리기는 매우 어렵다(원격 저장소에 주기적으로 푸시한다면 더더욱 안전하다). 덕분에 개발자는 시스템이 망가질 걱정 없이 과감하게 실험하고 언제든 되돌릴 수 있다.

## 5. 반드시 기억해야 할 3가지 상태와 3가지 영역

Pro Git 1장을 마무리하며 저자가 "_앞으로의 모든 학습을 순탄하게 하려면 이 부분만큼은 꼭 기억하라_"고 당부하는 핵심 개념이다.

### 파일의 3가지 상태 (The Three States)

Git이 관리하는 파일은 다음 세 가지 상태 중 하나에 놓인다.

1. **Modified (수정됨)**: 파일을 수정했지만 아직 로컬 데이터베이스에 커밋하지 않은 상태.
2. **Staged (스테이징됨)**: 수정한 파일의 현재 버전을 다음 커밋 스냅샷에 포함하도록 표시해 둔 상태.
3. **Committed (커밋됨)**: 데이터가 로컬 데이터베이스에 안전하게 영구 저장된 상태.

### Git 프로젝트의 3가지 영역 (The Three Sections)

이 세 가지 상태는 Git 프로젝트의 세 가지 물리적·논리적 영역으로 직결된다.

1. **Working Tree (워킹 트리)**
   - 프로젝트의 특정 버전 하나를 체크아웃해 놓은 작업 공간이다. Git 디렉토리 내부의 압축된 데이터베이스에서 파일들을 꺼내 디스크 위에 펼쳐놓은 상태이며, 개발자가 실제로 코드를 읽고 수정하는 곳이다.
2. **Staging Area (스테이징 영역)**
   - 다음 커밋에 들어갈 정보들을 미리 담아두는 파일이다. 보통 Git 디렉토리 내부에 위치하며, Git의 기술적인 용어로는 **Index**(인덱스)라고 부른다.
3. **Git Directory (`.git` 디렉토리)**
   - 프로젝트의 메타데이터와 객체 데이터베이스가 저장되는 **Git의 심장**이다. 다른 컴퓨터에서 저장소를 `clone`할 때 실제로 복사해 오는 본체가 바로 이 디렉토리다.

```text
[Working Tree]  --- (git add) --->  [Staging Area (Index)]  --- (git commit) --->  [Git Directory (.git)]
   Modified                                 Staged                                       Committed
```

기본적인 Git 워크플로우는 결국 이 세 영역 사이를 이동하는 과정이다. Working Tree에서 파일을 수정하고(`Modified`), 다음 커밋에 넣고 싶은 변경 사항만 선별해 Staging Area에 올린 뒤(`Staged`), 커밋을 실행해 Staging Area에 담긴 스냅샷 그대로 Git Directory에 영구 저장(`Committed`)한다.

## 마치며

1장만 제대로 이해해도 Git에 대한 막연한 두려움의 절반은 사라진다. Git이 파일을 diff 덩어리가 아니라 **내용의 SHA-1 해시로 인덱싱된 스냅샷 스트림**으로 저장하며, **Working Tree – Index – `.git` 디렉토리**라는 세 영역을 통해 상태를 전이시킨다는 점만 명확히 잡아두면 복잡한 명령어들도 자연스럽게 논리적으로 연결된다.

다음 편에서는 Pro Git 2장과 이후 챕터들을 따라가며, 실제로 로컬에 저장소를 초기화하고 파일의 생명주기를 추적할 때 `.git` 디렉토리와 Index 내부에서 무슨 일이 벌어지는지 더 깊게 들여다본다.
