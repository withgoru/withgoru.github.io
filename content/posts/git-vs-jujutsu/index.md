열심히 새로운 기능을 개발하고 있는데 갑자기 슬랙 알림이 울려. "지금 당장 프로덕션 핫픽스 하나만 처리해 주세요!"

이 순간 우리 머릿속은 복잡해지기 시작하지. 작업 중이던 더러운 워킹 트리를 `git stash`로 급하게 숨기거나, 임시 커밋을 날리고 브랜치를 이동해. 그러다 리베이스(Rebase)라도 잘못해서 충돌(Conflict)이 터지면? 터미널에 시뻘건 경고창이 뜨면서 충돌을 다 해결하기 전까진 아무것도 못 하는 '작업 정지' 상태에 빠지고 말아.

우리가 매일 당연하게 겪는 이 고통, 과연 우리가 Git을 못 써서 겪는 문제일까?

최근 구글 엔지니어가 주도해 개발한 차세대 버전 관리 시스템 **Jujutsu(줄여서 `jj`)**를 써보면 생각이 완전히 달라질 거야. **"원래 버전 관리는 이렇게 동작했어야 하는 거 아닌가?"**라는 탄성이 절로 나오거든.

오늘은 Git과 100% 호환되면서도 개발자의 작업 흐름을 완전히 바꿔놓고 있는 Jujutsu의 핵심 특징을 파헤쳐 보고, 기존 Git과 무엇이 다른지, 그리고 어떤 상황에 도입하면 좋을지 명확하게 정리해 줄게.

---

## 📌 본격적인 비교에 앞서: VCS와 DVCS 이해하기

본론으로 들어가기 전에, 우리가 쓰는 도구들의 정체성을 명확히 짚고 넘어갈 필요가 있어.

- **VCS (Version Control System, 버전 관리 시스템)**
  - 파일의 변화를 시간에 따라 기록해 특정 시점의 버전을 다시 불러올 수 있는 시스템 전체를 통칭하는 포괄적인 개념이야.
  - 과거의 SVN이나 CVS처럼 중앙 서버 한곳에만 모든 히스토리를 저장하는 **중앙 집중식 VCS(CVCS)**도 이 범주에 속해.

- **DVCS (Distributed Version Control System, 분산 버전 관리 시스템)**
  - 중앙 서버뿐만 아니라 개발자의 로컬 컴퓨터에도 저장소의 전체 히스토리와 브랜치가 통째로 복제되는 구조를 말해.
  - 네트워크 연결이 없어도 로컬에서 자유롭게 커밋, 브랜칭, 로그 조회가 가능하지.
  - 대표적인 DVCS로 **Git**과 **Mercurial(Hg)**이 있고, 오늘 소개할 **Jujutsu(`jj`)** 역시 바로 이 분산 버전 관리 시스템(DVCS) 계열의 최신 주자야.

즉, **Git과 Jujutsu는 둘 다 강력한 분산 버전 관리 시스템(DVCS)**이지만, 개발자가 도구를 다루는 인터페이스와 내부 멘탈 모델에서 혁신적인 차이가 나. 어떤 차이가 있는지 하나씩 살펴볼까?

## 1. Jujutsu(jj)가 대체 뭐길래? 핵심 특징 5가지

Jujutsu는 Git의 복잡한 사용성을 걷어내고 직관적인 멘탈 모델을 제공하는 차세대 VCS(버전 관리 시스템)야. 가장 놀라운 점은 **내부 스토리지 백엔드로 기존 Git을 그대로 사용한다**는 거지. 즉, 회사나 팀이 Git을 쓰고 있어도 내 로컬 컴퓨터에서만 `jj`를 깔아서 아무런 문제 없이 협업할 수 있어.

### ① `git add`와 `git stash`의 소멸 (워킹 카피 = 커밋)

Git은 내 파일 시스템과 데이터베이스 사이에 '스테이징 영역(Index)'이라는 징검다리가 있어. 그래서 파일을 수정하면 반드시 `git add`를 거쳐야만 하지.

반면, jj에는 스테이징 영역도, `stash`도 아예 존재하지 않아. **현재 내가 작업 중인 상태(Working copy) 자체가 하나의 실제 커밋**으로 취급되거든. 터미널에 `jj` 명령어를 칠 때마다 알아서 현재 파일 상태가 스냅샷으로 자동 기록돼. 작업 도중 다른 곳으로 이동하고 싶으면 그냥 이동하면 끝이야. 숨기고 자시고 할 게 없지.

### ② 커밋이 바뀌어도 끝까지 추적하는 'Change ID'

Git에서 과거 커밋 메시지를 수정(`amend`)하거나 리베이스를 하면 커밋 해시(Commit ID)가 아예 새로 바뀌어버려.

하지만 jj는 커밋마다 변하지 않는 고유 식별자인 **Change ID**를 부여해. 흥미로운 디테일은 Git의 16진수 해시(`0~9`, `a~f`)와 눈으로 구분하기 쉽게 **알파벳 `k`부터 `z`까지의 16개 문자만 사용**한다는 점이야. 커밋 내용을 수십 번 뜯어고쳐서 내부 Git 해시가 계속 바뀌어도 이 Change ID는 그대로 유지돼. 덕분에 `jj evolog` 명령어를 치면 특정 작업(Change) 하나가 처음부터 지금까지 어떻게 변해왔는지 그 역사를 한눈에 추적할 수 있어.

### ③ 충돌이 나도 멈추지 않는다: 일급 충돌 (First-class Conflicts)

개인적으로 jj에서 가장 충격적이었던 기능이야. Git은 머지나 리베이스 도중 충돌이 나면 그 자리에서 모든 작업이 올스톱되잖아?

jj는 **충돌이 난 상태 그 자체도 하나의 정상적인 커밋으로 저장**해 버려. 리베이스하다가 충돌이 15개쯤 터졌는데 당장 급한 미팅이나 핫픽스가 들어왔다면? 그냥 충돌 난 커밋을 그대로 놔두고 `jj new`로 다른 커밋으로 이동해서 급한 일부터 처리하면 돼. 충돌 해결은 나중에 커피 한잔 마시고 와서 여유롭게 처리한 뒤 `jj squash`로 밀어 넣으면 그만이야.

### ④ 브랜치 이름 짓기 지옥에서 해방: 북마크(Bookmark)

로컬에서 사소한 실험이나 기능 개발을 할 때마다 브랜치 이름을 짓느라 고민해 본 적 있지? jj는 기본적으로 이름 없는 '익명 브랜치(정확히는 Change ID)' 상태로 가볍게 커밋을 쌓아 올리며 작업해.

Git의 브랜치 개념 대신 특정 커밋에 포스트잇을 붙여두는 듯한 **북마크(Bookmark)** 개념을 사용하는데, 로컬에서 마음껏 작업하다가 원격 저장소(GitHub 등)에 PR을 올릴 때만 북마크를 달아서 푸시하면 돼. 심지어 `jj git push -c`를 쓰면 Change ID를 기반으로 북마크 이름을 자동 생성해서 푸시까지 한 번에 해결해 줘.

### ⑤ 두려움 없는 시간 여행: `jj undo`와 Operation Log

Git에서 리베이스를 잘못해서 브랜치가 날아갔을 때, 등골이 서늘해지며 스택오버플로우에서 `git reflog` 복구법을 검색해 본 경험이 다들 있을 거야.

jj에서는 어떤 실수를 하든 **`jj undo` 한 방이면 직전 상태로 완벽하게 되돌아갈 수 있어.** 더 과거로 가고 싶다면 `jj op log`(Operation Log)를 열어 저장소를 처음 만들었던 시점부터 지금까지의 모든 명령어 기록을 확인하고, `jj op restore <ID>`로 원하는 시간대로 손쉽게 타임머신을 탈 수 있지.

## 2. Jujutsu 실전 워크플로우 맛보기

jj를 쓰면 코드를 짜는 사고방식 자체가 훨씬 유연해져. 실무에서 가장 많이 쓰는 패턴 3가지를 짧게 보여줄게.

### 패턴 1: 스쿼시(Squash) 워크플로우

현재 비어 있는 작업 커밋을 일종의 '작업대'처럼 쓰는 방식이야. 일단 코드를 막 짜고 나서, 원하는 변경 사항만 골라 부모 커밋이나 특정 과거 커밋으로 쏙쏙 밀어 넣는 거지.

```bash
# 새로운 빈 작업 커밋 생성
jj new

# 파일 수정 후, 변경 사항 중 원하는 부분만 골라 직전(부모) 커밋에 합치기
jj squash -i

# 특정 과거 커밋(예: Change ID가 kxyz)으로 변경 사항 밀어 넣기
jj squash --into kxyz
```

### 패턴 2: Edit 워크플로우 (과거 커밋 직접 수정)

과거의 특정 커밋으로 이동해서 수정하고 싶다면 `jj edit <ID>`를 쓰면 돼. 해당 시점으로 돌아가 코드를 수정한 뒤 저장하면, 그 위에 쌓여 있던 자식 커밋들이 자동으로 리베이스되거든.

만약 커밋 순서를 바꾸거나 특정 커밋 사이에 내 커밋을 끼워 넣고 싶다면 내가 직접 체크아웃할 필요도 없어. 리베이스 명령어의 플래그 하나로 원격 조종하듯 꽂아 넣으면 끝이야.

```bash
# yx 커밋을 tu 커밋 뒤, 그리고 r 커밋 앞으로 쏙 끼워 넣기
jj rebase -r yx --insert-after tu --insert-before r
```

### 패턴 3: 파워 유저들의 비기, 메가머지(Mega-merge)

모노레포 환경이나 여러 피처를 동시에 건드려야 할 때 빛을 발하는 워크플로우야. Git에서는 워크트리(Worktree)로 폴더를 여러 개 쪼개야 했지만, jj에서는 여러 개의 피처 브랜치를 한꺼번에 부모로 갖는 통합 커밋을 만들어서 한 공간에서 작업할 수 있어.

```bash
# 3개의 서로 다른 피처(ntt, ym, tx)를 동시에 부모로 갖는 통합 작업 공간 생성
jj new ntt ym tx
```

이렇게 합쳐진 환경에서 코드를 짜고 테스트하다가, "아, 방금 짠 코드는 ntt 피처에 들어가야겠네" 싶으면 `jj squash --into ntt`나 `jj rebase`로 해당 줄기에 가볍게 내려보내면 돼.

## 3. 한눈에 보는 Git vs Jujutsu 비교

두 도구의 차이점을 표로 깔끔하게 정리해 봤어.

| 비교 항목               | Git                                             | Jujutsu (`jj`)                                           |
| :---------------------- | :---------------------------------------------- | :------------------------------------------------------- |
| **작업 상태 관리**      | 워킹 디렉토리 → `add` → `commit`                | 워킹 카피 자체가 자동 커밋됨 (`add`, `stash` 없음)       |
| **커밋 식별자**         | 불변하는 Commit Hash (`0~9`, `a~f`)             | Commit Hash + 끝까지 추적되는 **Change ID** (`k~z`)      |
| **브랜치 전략**         | 작업 전 브랜치 생성 및 체크아웃 필수            | 익명 커밋으로 자유롭게 작업 후 푸시할 때만 Bookmark 지정 |
| **충돌(Conflict) 처리** | 충돌 발생 시 즉각 해결 전까지 작업 중단         | 충돌 상태 그대로 커밋 가능 (나중에 원할 때 해결)         |
| **히스토리 수정**       | 과거 커밋 수정 시 수동 리베이스 필요            | 과거 커밋(`jj edit`) 수정 시 하위 커밋 자동 리베이스     |
| **실수 복구 (Undo)**    | `git reset`, `git reflog` 등 복구 과정이 복잡함 | 직관적인 `jj undo` 및 `jj op log` 완벽 지원              |

## 4. 어떤 상황에 무엇을 써야 할까? (도입 가이드)

그렇다면 당장 오늘부터 Git을 버리고 jj로 넘어가야 할까? 각 도구가 어울리는 상황과 명확한 한계점을 짚어줄게.

### 👍 이럴 땐 주저 없이 Jujutsu(jj)를 써봐!

- **로컬 개발 생산성과 커밋 관리를 극대화하고 싶을 때**: jj는 `jj git init --colocate` 명령어를 통해 기존 Git 저장소 위에서 그대로 돌아가. 팀원들에게 눈치 보지 않고 나 혼자 로컬에서 깔끔하게 커밋을 쪼개고 리베이스하는 용도로 쓰기에 완벽해. (기존 Git 커밋들도 해시 기반의 결정론적 알고리즘을 통해 동일한 Change ID로 매핑되니까 호환성 걱정은 안 해도 돼.)
- **잦은 컨텍스트 스위칭과 충돌에 지쳤을 때**: 하루에도 몇 번씩 PR 리뷰 요청이 들어오고, 여러 브랜치를 오가며 동시에 여러 기능을 개발해야 하는 환경이라면 jj의 스태시 없는 이동과 메가머지 워크플로우가 구원투수가 되어줄 거야.
- **깔끔한 커밋 히스토리(선형 히스토리)에 집착할 때**: PR을 올리기 전에 커밋을 예쁘게 쪼개고 다듬는 걸 좋아한다면, 자유자재로 과거를 수정하고 인터디프(`jj interdiff`)로 버전 간 차이점까지 비교해 주는 jj가 최고의 선택이야.

### ⚠️ 이럴 땐 아직 순수 Git에 머물러야 해!

아무리 jj가 훌륭해도 아직 명확한 기술적 한계점이 존재해. jj는 내부적으로 Git 데이터를 다룰 때 자체 Rust 기반 라이브러리(`gitoxide` 등)를 거치기 때문에, 순수 Git CLI가 가진 모든 부가 기능을 100% 구현하지는 못했거든.

- **Git LFS를 사용하는 프로젝트**: 대용량 에셋을 다루는 게임 개발이나 데이터 프로젝트처럼 Git LFS(Large File Storage)가 필수인 곳에서는 아직 jj가 이를 지원하지 않아 사용할 수 없어.
- **.gitattributes나 Submodule 의존도가 높을 때**: `.gitignore`는 완벽하게 호환되지만, `.gitattributes`를 통한 복잡한 파일 처리나 Git 서브모듈(Submodule)을 헤비하게 쓰는 환경이라면 도입을 미루는 게 좋아.
- **GUI 툴 의존도가 높은 개발자**: 아직 소스트리(SourceTree)나 GitKraken 같은 대중적인 GUI 생태계가 부족해. 터미널(CLI) 환경이 친숙하지 않다면 진입장벽이 느껴질 수 있어.

## 마치며

Jujutsu는 기존 Git 생태계를 파괴하는 도구가 아니라, Git이라는 강력한 엔진 위에 개발자 친화적인 최신식 운전석을 얹어준 도구야.

LFS를 쓰는 특수한 프로젝트가 아니라면, 지금 작업 중인 사이드 프로젝트나 회사 로컬 저장소에 가볍게 jj를 연동해서 써보는 건 어떨까? 한 번이라도 `jj undo`와 `jj squash`의 손맛을 보고 나면, 다시는 예전의 빡빡했던 Git 명령어로 돌아가기 쉽지 않을 거야.
